# ADR-002: Use NestJS for the API

## Decision

Build `apps/api` with NestJS instead of raw Node's `http` module, Express,
or Fastify.

## Problem

Raw Node's `http` module gives you a socket and nothing else: no routing,
no automatic body parsing, no response serialization, and no opinion about
where code should live. That's fine for a handful of routes. As route
count grows, there is nothing structural stopping request-handling code,
validation, and business logic from all collapsing into the same function.
The framework doesn't create this problem — it just doesn't prevent it,
and on a deadline, the path of least resistance is to keep adding to
whatever function already handles the route.

## Alternatives

**Raw Node `http`** — no framework at all; hand-roll routing, body
parsing, and response handling.

**Express** — minimal, unopinionated routing and middleware framework.
Extremely popular, minimal structure imposed.

**Fastify** — similar to Express in philosophy (routing + middleware/plugins),
but faster and with built-in schema-based validation and serialization.

**NestJS** — a framework built on top of Express (or Fastify) that adds a
module/controller/service structure and a dependency injection container on
top of the underlying HTTP layer.

## Pros

- **Raw Node `http`:** zero dependencies, nothing to learn, full control
  over every byte of the request/response cycle.
- **Express:** minimal learning curve, huge ecosystem, easy to understand
  because there's very little framework to understand.
- **Fastify:** Express-like simplicity with better performance and
  built-in request/response schema validation.
- **NestJS:** gives structure by default — modules, controllers, services,
  and dependency injection are generated by the CLI, not invented by hand.
  Strong TypeScript support throughout.

## Cons

- **Raw Node `http`:** every project reinvents routing, body parsing, and
  error handling from scratch. No structural guidance at all — the exact
  problem this ADR exists to solve.
- **Express:** unopinionated by design, which is a pro for a five-route API
  and a con as the app grows — there is no default answer for "where does
  this logic go," so it goes wherever is fastest to write in the moment.
- **Fastify:** same structural looseness as Express; the built-in
  validation is a real benefit, but it doesn't address where business logic
  should live any more than Express does.
- **NestJS:** steep learning curve for a beginner — decorators (`@Module`,
  `@Controller`, `@Injectable`), dependency injection, and metadata
  reflection are all new concepts at once. The decorator/DI style obscures
  control flow: reading a controller doesn't tell you how its service got
  instantiated or what else depends on it — you have to trust the
  framework's wiring. It is more ceremony than a five-endpoint API strictly
  needs. And Nest is a poor fit for tiny services or serverless functions,
  where cold-start time and minimal footprint matter more than structure —
  bootstrapping Nest's DI container on every cold start is real overhead
  that a single Express handler doesn't pay.

## Tradeoffs

Choosing Nest trades runtime simplicity and a gentle learning curve for
structural guardrails. The bet is that those guardrails pay for themselves
as Neuron grows past a handful of endpoints (auth, entries, search, RAG,
scheduled jobs — see the roadmap), at the cost of a harder Day 2–3 for
someone who has never used Nest before.

## Reasoning

To be honest about what Nest actually buys: **Nest does not force good
structure.** It is entirely possible to write a bloated controller method
in Nest exactly the way you can in Express — nothing in the framework
prevents a developer from putting business logic directly in a
`@Controller` method instead of delegating to a service. What Nest changes
is the *default path*. Running `nest g resource` generates a module, a
controller, and a service as separate files, wired together with
dependency injection, before you've written a single line of business
logic. Following the path of least resistance in Nest means following the
CLI's generators — and the CLI's generators produce separated
controller/service files. In Express or Fastify, the path of least
resistance is to add one more route handler to whatever file already has
routes in it, because there's no generator suggesting otherwise.

For a beginner specifically, this matters more than it would for someone
who already has internalized structure from experience: the framework's
generated shape becomes the example to learn from, rather than something
that has to be imposed by discipline alone. The cost — decorators and DI as
unfamiliar concepts — is accepted because "what does a well-structured
backend look like" is a primary learning goal of this project (see the
roadmap's stated emphasis on backend architecture), and Nest's defaults
answer that question by example on every file the CLI generates.

## Final Decision

Use NestJS for `apps/api`.

## Future Revisit Conditions

None expected within this project. Nest would become the wrong choice if
the project's shape changed to something Nest is a poor fit for — for
example, if the API were decomposed into small serverless functions where
cold-start latency dominates, or if the team ever needed to onboard
contributors for whom Nest's decorator/DI style was actively slowing
delivery down with no corresponding structural benefit being felt. Neither
is expected to become true during Neuron's 30-day build.
